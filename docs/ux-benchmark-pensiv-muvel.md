# 펜시브·뮤블 PC 웹 UX 벤치마킹

- 작성일: 2026-08-25
- 대상: [펜시브(pensiv)](https://app.pensiv.so/), [뮤블(Muvel)](https://muvel.app/ko)
- 분석 범위: PC 웹의 정보 구조, 핵심 사용자 흐름, 작업 화면, 내비게이션, 시각 디자인
- 프로젝트 목표: Lorekeeper 프론트엔드를 처음부터 다시 설계·구현하기 위한 UX 참고 자료

## 1. 프로젝트 전제

이번 벤치마킹의 목표는 펜시브나 뮤블과 비슷한 화면을 만드는 것이 아니다.

> 두 서비스에서 검증된 사용자 경험의 원리를 채용하되, 화면의 시각적 표현과 컴포넌트 체계는 Lorekeeper 고유의 방식으로 다시 설계한다.

기존 프론트엔드 구조와 UI를 유지한다는 전제를 두지 않는다. 필요한 페이지, 정보 구조, 내비게이션과 상호작용을 처음부터 다시 정의하고 구현한다.

벤치마킹 결과는 다음과 같이 구분해서 사용한다.

| 채용할 수 있는 UX | 그대로 복제하지 않을 UI |
| --- | --- |
| 프로젝트 중심의 진입 흐름 | 동일한 화면 배치와 영역 비율 |
| 작업 맥락을 유지하는 탭·분할 개념 | 동일한 탭·패널 모양과 배치 |
| 원고와 설정을 빠르게 왕복하는 흐름 | 동일한 사이드바 트리 디자인 |
| 기능을 단계적으로 노출하는 방식 | 동일한 아이콘 위치와 툴바 구성 |
| 자동 저장과 동기화 상태 피드백 | 동일한 색상, 타이포그래피와 효과 |
| 작가에게 익숙한 콘텐츠 용어 | 동일한 문구, 라벨과 마이크로카피 |
| 오류의 근거를 원고 맥락에서 확인하는 방식 | 동일한 카드, 모달, 드로어 컴포넌트 |

단순히 색상이나 모서리만 바꾸는 것은 충분한 재설계가 아니다. 정보 위계, 컴포넌트 표현, 브랜드 언어와 상호작용 피드백을 Lorekeeper의 핵심 기능에 맞게 의미 있게 재구성해야 한다.

## 2. 조사 방법과 한계

로그인 전 화면은 PC 해상도에서 직접 확인했다. 로그인 이후 작업 화면은 각 서비스가 제공하는 최신 공식 문서, 공식 가이드와 공식 화면 이미지를 함께 분석했다.

계정과 실제 작품 데이터가 필요한 다음 항목은 이번 조사 범위에 포함하지 않았다.

- 신규 가입 완료율과 인증 실패 처리
- 실제 프로젝트 생성에 걸리는 단계와 시간
- 대용량 원고에서의 성능
- 자동 저장 및 충돌 상황의 실제 동작
- 유료 기능의 제한과 결제 전환 흐름
- 장시간 사용자를 대상으로 한 사용성 테스트

따라서 이 문서는 정량적 사용성 평가가 아니라 제품 구조와 디자인 패턴에 대한 휴리스틱 벤치마킹이다.

## 3. 핵심 결론

두 서비스는 모두 단순 문서 편집기가 아니라 원고, 설정과 플롯을 한 프로젝트에서 관리하는 작가용 워크스페이스다. 다만 최적화한 문제가 다르다.

- 펜시브는 작품의 구조, 파일 간 연결과 프로젝트 진행 상태를 관리하는 데 강하다.
- 뮤블은 실제 집필 편의, 여러 자료를 동시에 참고하는 작업과 개인별 작업 환경 구성에 강하다.
- Lorekeeper에는 펜시브의 구조적 안정성과 뮤블의 집필 편의성을 UX 원리로 채용한다.
- UI는 설정 오류 탐지와 근거 확인이라는 Lorekeeper 고유 과업을 중심으로 새롭게 설계한다.
- 초기 제품에서는 원고·설정·플롯·메모의 네 가지 핵심 개념으로 시작하고 고급 구조는 단계적으로 추가한다.
- 최종 화면을 두 서비스의 스크린샷과 나란히 놓았을 때 단순 변형판처럼 보인다면 재설계가 부족한 것으로 판단한다.

## 4. 서비스 정보 구조

### 4.1 펜시브

```text
로그인
└─ 전체 프로젝트
   ├─ 새 프로젝트
   │  ├─ 빈 프로젝트
   │  └─ 예제·템플릿
   └─ 프로젝트 홈
      ├─ 최근 파일·할 일
      ├─ 문서
      ├─ 캐릭터·설정 시트
      ├─ 플롯보드
      ├─ 캔버스
      ├─ 노트
      ├─ 관계 그래프
      └─ 작업 관리
```

펜시브는 파일이 아니라 프로젝트에서 시작한다. 프로젝트를 만든 뒤 그 안에서 문서, 캐릭터, 플롯과 작업을 만든다. 빈 프로젝트 외에 예제와 구조 템플릿을 제공하여 처음 사용하는 사람이 완성된 구조를 먼저 경험할 수 있게 한다.

| 파일 유형 | 역할 | 대표 사용 사례 |
| --- | --- | --- |
| 문서 | 서술과 원고 작성 | 장면, 에피소드, 초고 |
| 시트 | 반복해서 참조할 정보 정의 | 인물, 장소, 사건, 아이템 |
| 플롯보드 | 이야기 순서와 단계 구성 | 막 구조, 장면 순서 |
| 캔버스 | 관계와 아이디어의 시각적 탐색 | 인물 관계, 감정선, 설정 충돌 |
| 노트 | 아직 정리되지 않은 생각 보관 | 아이디어, 가설, 임시 메모 |

펜시브의 파일 유형은 저장 형식보다 생각의 역할을 구분한다. 하나의 생각이 노트에서 시작해 플롯보드와 문서로 이동하고, 시트나 캔버스와 연결되는 흐름을 전제로 한다.

### 4.2 뮤블

```text
랜딩
└─ 키뮤스토리 통합 로그인
   └─ 소설 프로젝트
      ├─ 에피소드
      ├─ 위키
      ├─ 플롯 캔버스
      ├─ 메모
      ├─ 일반 에디터
      └─ 워크스페이스 에디터
         ├─ 여러 문서 분할
         ├─ 탭
         └─ 위젯 보드
```

뮤블은 작가에게 익숙한 에피소드, 위키와 메모를 중심으로 프로젝트를 구성한다.

| 영역 | 역할 | 대표 사용 사례 |
| --- | --- | --- |
| 에피소드 | 스토리와 원고 관리 | 웹소설 회차, 챕터, 장면 |
| 위키 | 확정된 설정 관리 | 인물, 세계관, 사건, 연표 |
| 플롯 캔버스 | 사건과 관계 시각화 | 플롯, 인물 관계, 분기 |
| 메모 | 임시 정보 기록 | 아이디어, 집필 중 참고사항 |
| 워크스페이스 | 여러 자료를 동시에 배치 | 원고+설정+캔버스+메모 |

에피소드에는 연령 등급과 서술 시점 같은 작품 속성을 부여할 수 있다. 목록의 우클릭 메뉴에서 열기, 이름 변경, 복제, 상태 변경, 버전 관리, 댓글, 워크스페이스 열기와 삭제를 실행할 수 있다.

## 5. PC 작업 화면 비교

### 5.1 공통 UX 골격

두 서비스는 모두 PC 화면에서 다음 세 가지 정보 관계를 유지한다.

```text
작품 구조 탐색
      ↓
원고 중심 작업 ─── 선택한 문장·설정·플롯의 맥락 정보
      ↓
진척·저장·검토 상태
```

공통적인 장점은 원고를 닫지 않고 설정과 플롯을 참조할 수 있다는 점이다. 차이는 보조 정보를 구성하는 방식에 있다.

- 펜시브는 파일과 탭을 패널에 열어 작업 맥락을 확장한다.
- 뮤블은 문서 패널과 사용자가 선택한 위젯을 함께 배치한다.

Lorekeeper는 이 정보 관계를 채용하되 동일한 3열 레이아웃이나 영역 비율을 복제하지 않는다. 탐색 영역, 작업 캔버스와 맥락 인스펙터의 표현 방식은 별도의 와이어프레임으로 설계한다.

### 5.2 펜시브 패널 구조

펜시브의 작업 패널은 위에서 아래로 다음 계층을 갖는다.

```text
탭 바
→ 파일 헤더
→ 편집 툴바
→ 주요 작업 영역
```

- 좌측 사이드바는 프로젝트 홈, 그래프, 작업, 노트와 파일 트리를 보여준다.
- 상단 탭은 사용자가 동시에 생각하고 있는 파일 집합을 유지한다.
- 파일 헤더는 경로, 상태, 태그, 연결 정보와 설정을 제공한다.
- 중앙 영역은 파일 유형에 따라 문서 편집기, 플롯보드, 시트와 캔버스로 바뀐다.
- 패널은 좌우 또는 상하로 분할하고 다시 확장할 수 있다.
- 탭 이동, 패널 잠금과 새 창 열기를 지원한다.

장점은 화면이 복잡해져도 각 계층의 역할이 일관된다는 것이다. 반면 탭, 파일 헤더와 툴바가 모든 패널에 반복되면 실제 원고 영역이 줄어들 수 있다.

### 5.3 뮤블 워크스페이스와 위젯

뮤블은 일반 에디터와 고급 워크스페이스 에디터를 구분한다. 워크스페이스에서는 여러 문서의 창을 분할하고 탭을 이동할 수 있다.

위젯은 다음과 같은 용도로 사용된다.

- 글자 수와 선택 위치 확인
- 다른 에피소드와 위키 참조
- 메모와 상용구 관리
- 사전과 특수문자 입력
- 타이머, 스톱워치, 집필 속도와 집중도 측정
- TTS와 빠른 스크롤
- 단락 및 반복 표현 분석

일반 위젯은 에디터 좌우 빈 공간에 배치하고, 짧은 상태 정보는 에디터 하단에 배치한다. 위젯은 드래그로 순서를 바꾸고 접거나 일부 크기를 조절할 수 있다.

이 방식은 숙련 사용자가 자신의 작업 환경을 만들 수 있다는 점에서 강력하다. 하지만 사용자가 무엇을 배치해야 하는지 결정해야 하고, 위젯이 늘수록 원고보다 도구가 강하게 보일 위험이 있다.

## 6. 핵심 사용자 흐름

### 6.1 펜시브

```text
로그인
→ 전체 프로젝트
→ 새 프로젝트
→ 빈 프로젝트 또는 예제 선택
→ 구조 템플릿 선택
→ 제목·설명 입력
→ 프로젝트 홈
→ 문서·캐릭터·플롯 생성
→ 탭과 분할 화면으로 작업
```

#### 장점

- 처음부터 작품 단위로 정보가 묶인다.
- 예제 프로젝트가 복잡한 구조를 설명하는 인터랙티브 튜토리얼 역할을 한다.
- 프로젝트 홈에서 최근 파일과 할 일을 확인하고 이전 맥락으로 복귀할 수 있다.
- 원고, 설정과 플롯을 동시에 유지하는 흐름이 제품 전체에서 일관된다.

#### 위험

- 사용자는 첫 원고를 쓰기 전에 프로젝트와 템플릿을 이해해야 한다.
- 문서, 시트, 플롯보드와 캔버스의 차이를 모르면 생성 단계에서 망설일 수 있다.
- 바로 글을 쓰고 싶은 사용자에게는 진입 절차가 길게 느껴질 수 있다.

### 6.2 뮤블

```text
랜딩
→ 로그인하고 글 쓰러 가기
→ 키뮤스토리 통합 로그인
→ 소설 프로젝트
→ 에피소드 생성
→ 원고 작성
→ 필요할 때 위키·메모·캔버스 추가
→ 고급 사용 시 워크스페이스와 위젯 구성
```

#### 장점

- 에피소드라는 익숙한 개념을 중심으로 빠르게 집필을 시작할 수 있다.
- 고급 기능을 나중에 사용하게 하여 기본 진입 부담을 낮춘다.
- 집필 중 필요한 보조 기능을 작업 화면에서 추가할 수 있다.

#### 위험

- 랜딩의 뮤블 브랜드에서 키뮤스토리 계정 화면으로 전환되면서 서비스 연결감이 약해진다.
- 일반 에디터와 워크스페이스 에디터의 차이를 별도로 학습해야 한다.
- 사용자별 위젯 구성이 달라지면 도움말과 고객 지원이 어려워질 수 있다.

| --- | --- | --- | --- |
| 기본 철학 | 구조와 연결 관계 관리 | 집필 과정과 작업 환경 최적화 | 오류 탐지를 원고 맥락에 연결한다. |
| 시작 방식 | 프로젝트와 템플릿 | 소설과 에피소드 | 최소 입력 후 첫 회차로 바로 이동한다. |
| 콘텐츠 분류 | 문서·시트·플롯·캔버스·노트 | 에피소드·위키·캔버스·메모 | 원고·설정·플롯·메모로 단순화한다. |
| 열린 작업 | 상단 탭 | 워크스페이스의 창과 탭 | 최근 작업 맥락을 잃지 않게 한다. |
| 보조 정보 | 다른 파일을 패널에 열기 | 위젯과 문서 패널 | 선택에 반응하는 맥락 인스펙터를 제공한다. |
| 빠른 실행 | 명령 팔레트와 단축키 | 우클릭 메뉴와 위젯 | 노출 액션과 키보드 흐름을 함께 제공한다. |
| 구조 이해 | 관계 그래프와 파일 연결 | 위키·캔버스 참조 | 오류 근거와 영향 범위를 중심으로 시각화한다. |
| 초기 난이도 | 비교적 높음 | 기본은 낮고 고급은 높음 | 기본 집필과 고급 분석을 단계적으로 분리한다. |

## 8. 시각 디자인 분석

### 8.1 펜시브

#### 특징

- 검정과 짙은 회색을 사용하고 강조색을 제한한다.
- 선택된 트리 항목, 파일 상태와 관계선에만 색상을 사용한다.
- 중앙 원고를 넓게 두고 도구의 시각적 존재감을 낮춘다.
- IDE나 Obsidian과 비슷한 전문 생산성 도구의 인상을 준다.

#### 장점

- 복잡한 프로젝트를 다루는 전문 도구라는 인상이 명확하다.
- 장식보다 콘텐츠와 구조에 시선이 간다.
- 상태 색상과 선택 상태를 통제하기 쉽다.

#### 주의점

- 장시간 읽기와 교정에서는 밝은 원고 배경을 선호하는 사용자도 많다.
- 비활성 텍스트의 명암이 낮으면 가독성과 접근성이 떨어질 수 있다.
- 아이콘과 얇은 구분선만 사용하면 기능 발견성이 낮아질 수 있다.

### 8.2 뮤블

#### 특징

- 랜딩과 로그인은 밝고 낮은 채도의 색상과 캐릭터 일러스트를 사용한다.
- 작업 화면은 흰색 패널, 얇은 회색 테두리와 상태별 강조색을 사용한다.
- 여러 창을 구분하기 위해 데스크톱 애플리케이션형 패널을 사용한다.
- 라이트·다크 모드, 배경, 글꼴, 줄 간격과 위젯 배치를 변경할 수 있다.

#### 장점

- 친근한 브랜드와 기능적인 작업 화면을 모두 제공한다.
- 여러 문서를 열었을 때 패널 경계가 분명하다.
- 집필 화면을 개인 취향에 맞출 수 있다.

#### 주의점

- 랜딩의 캐릭터 중심 인상과 실제 전문 작업 화면 사이의 차이가 크다.
- 패널 테두리, 툴바와 아이콘이 많아지면 시각적 밀도가 높아진다.
- 커스터마이징을 지나치게 허용하면 기본 디자인의 일관성이 약해진다.

## 9. UI 상세 분석 — 참고용

이 장은 구현 명세나 디자인 확정안이 아니다. 경쟁 서비스가 UX를 어떤 UI 요소로 표현했는지 관찰하고, 이후 Lorekeeper 와이어프레임과 디자인 시스템을 만들 때 참고하기 위한 자료다.

수치와 배치는 공식 화면을 기준으로 한 시각적 관찰이며 그대로 적용하지 않는다.

### 9.1 펜시브 UI

#### 로그인 화면

| 항목 | 관찰 결과 | 효과 | 참고 시 주의점 |
| --- | --- | --- | --- |
| 배경 | 거의 단색에 가까운 어두운 전체 화면 | 시선이 인증 영역에 바로 모임 | Lorekeeper가 같은 검정 배경을 사용할 필요는 없음 |
| 로고 | 중앙 상단에 세리프 워드마크 배치 | 차분하고 문학적인 인상 | 동일한 서체 조합과 크기 비율은 복제하지 않음 |
| 인증 버튼 | Google·Apple·이메일을 동일한 폭의 세로 버튼으로 배치 | 선택지가 단순하고 비교하기 쉬움 | 버튼 모양과 순서를 그대로 따르지 않음 |
| 보조 정보 | 약관은 화면 하단, 버전은 우측 하단에 낮은 대비로 표시 | 핵심 행동을 방해하지 않음 | 낮은 대비가 접근성 기준을 벗어나지 않게 검증 필요 |
| 정보 밀도 | 매우 낮음 | 빠른 판단과 집중에 유리 | 서비스 가치 설명이 필요한 신규 사용자에게는 지나치게 비어 보일 수 있음 |

펜시브 로그인 화면은 인증 이외의 선택을 거의 제거한다. 기존 사용자에게는 빠르지만, 처음 방문한 사용자가 제품의 효용을 이해하는 데 필요한 정보는 별도의 랜딩에 의존한다.

#### 애플리케이션 셸

```text
상단: 앱 제어·통합 검색·상태
좌측: 프로젝트 전환·주요 메뉴·파일 트리
중앙: 파일 헤더·편집 툴바·원고
우측: 댓글·참조·보조 정보
```

| 영역 | UI 구성 | 시각적 특징 | UX 역할 |
| --- | --- | --- | --- |
| 상단 바 | 프로젝트 경로, 검색, 상태·도구 아이콘 | 높이가 낮고 배경과 유사한 색 | 전역 기능을 차지하는 공간을 최소화 |
| 좌측 사이드바 | 홈·그래프·작업, 설정별 폴더, 문서 트리 | 작은 아이콘, 들여쓰기, 선택 행 배경 | 작품 전체 구조와 현재 위치 표시 |
| 중앙 편집기 | 제목, 본문, 간결한 툴바 | 화면 중앙에 제한된 본문 폭, 넓은 여백 | 장문 가독성과 집필 집중 |
| 우측 패널 | 댓글 또는 보조 문서 | 독립된 어두운 패널과 헤더 | 원고를 닫지 않고 관련 맥락 확인 |
| 하단 메뉴 | 휴지통, 가져오기, 내보내기, 설정 | 좌측 트리 하단에 보조 기능 배치 | 주요 집필 흐름과 관리 기능 분리 |

#### 색상과 대비

- 짙은 무채색이 화면 대부분을 차지한다.
- 선택된 파일, 상태, 태그와 관계선에만 제한적으로 색을 사용한다.
- 패널 구분은 강한 그림자보다 미세한 명도 차이와 얇은 선을 사용한다.
- 본문은 완전한 흰색보다 부드러운 밝은 회색에 가깝고, 보조 텍스트는 대비를 낮춘다.
- 상태 색이 장식색과 구분되어 복잡한 화면에서도 의미를 갖는다.

참고할 점은 색의 개수가 아니라 **색상을 상태와 선택에만 집중해서 사용하는 규칙**이다. 동일한 어두운 팔레트를 복제할 필요는 없다.

#### 타이포그래피

- 브랜드 워드마크에는 문학적 인상의 세리프 계열을 사용한다.
- 애플리케이션 UI와 본문에는 읽기 쉬운 산세리프 계열을 사용한다.
- 원고 제목은 크기와 굵기로 명확하게 분리하고, 본문은 비교적 긴 줄 간격을 사용한다.
- 메뉴와 툴바 텍스트는 작게 유지하여 원고보다 시각적 우선순위가 낮다.

브랜드와 제품 UI의 서체 역할을 분리한 점은 참고할 수 있다. 다만 지나치게 작은 보조 텍스트와 낮은 대비는 장시간 사용 시 피로를 만들 수 있다.

#### 컴포넌트와 상태 표현

- 파일 트리는 폴더, 문서 종류, 들여쓰기와 선택 행으로 위계를 표현한다.
- 상단 툴바는 문자 수, 글꼴, 크기와 줄 간격처럼 현재 원고와 직접 관련된 기능만 노출한다.
- 태그와 상태는 작은 칩 또는 아이콘으로 표현한다.
- 검색은 앱 최상단 중앙에 두어 전역 기능임을 강조한다.
- 댓글 패널은 원고와 비슷한 배경을 사용하지만 패널 경계로 맥락을 분리한다.

아이콘 비중이 높기 때문에 숙련 사용자에게는 빠르지만 신규 사용자에게는 기능을 발견하기 어려울 수 있다. Lorekeeper에서는 핵심 액션의 텍스트 레이블과 툴팁을 함께 검토해야 한다.

#### 타임라인 화면

- 동일한 폴더를 그리드·리스트·보드·타임라인으로 전환하는 보기 탭을 제공한다.
- 타임라인은 상태별로 색이 다른 가로 레일을 사용한다.
- 각 회차는 제목, 요약, 상태가 포함된 카드로 레일 위에 배치된다.
- 색상뿐 아니라 상태 텍스트도 함께 표시해 의미를 보완한다.
- 넓은 PC 화면을 시간 축과 카드 배치에 적극 활용한다.

참고할 UX는 **동일한 데이터를 목적에 따라 다른 보기로 전환하는 방식**이다. 레일 색, 카드 모양과 탭 구성을 동일하게 만들 필요는 없다.

#### 펜시브 UI의 강점과 위험

| 강점 | 위험 |
| --- | --- |
| 원고가 항상 가장 높은 시각적 우선순위를 가짐 | 어두운 화면과 낮은 대비가 모든 사용자에게 적합하지 않음 |
| 파일 트리와 열린 탭의 역할이 명확함 | 아이콘 중심 기능은 발견성이 낮음 |
| 제한된 강조색으로 복잡도를 통제함 | 문서가 많아지면 트리의 세로 밀도가 급격히 증가함 |
| 넓은 화면에서 원고와 참조 정보를 함께 유지함 | 좌우 패널이 동시에 열리면 본문 폭이 좁아짐 |
| 패널 구조가 파일 유형과 무관하게 일관됨 | 반복되는 패널 헤더와 툴바가 공간을 소비함 |

### 9.2 뮤블 UI

#### 랜딩과 로그인 화면

| 항목 | 관찰 결과 | 효과 | 참고 시 주의점 |
| --- | --- | --- | --- |
| 랜딩 톤 | 어두운 보라 계열 배경과 큰 제품 미리보기 | 창작 도구의 감성적 인상 제공 | 펜시브와 다른 어두운 계열이지만 고유 팔레트 필요 |
| 로그인 배경 | 밝은 청회색과 매우 큰 장식 텍스트 | 화면이 비어 보이지 않고 브랜드 분위기 형성 | 큰 배경 글자가 작은 화면에서 방해되지 않게 해야 함 |
| 인증 영역 | 중앙 세로 열에 네 가지 소셜 로그인 배치 | 선택 구조가 단순함 | 소셜 로그인 수가 많아 우선순위가 흐려질 수 있음 |
| 캐릭터 | 우측 하단에 큰 캐릭터 일러스트와 말풍선 | 친근함과 기억 가능성 강화 | 전문 작가 대상 신뢰와 충돌할 가능성 있음 |
| 전역 제어 | 우측 상단에 언어와 테마 버튼 | 진입 전 접근성·개인화 제공 | 아이콘 의미를 툴팁 없이 이해하기 어려울 수 있음 |

뮤블은 로그인 단계에서도 브랜드 캐릭터를 적극적으로 보여준다. 펜시브보다 친근하지만, 작업 화면의 기능적 디자인과 감성적 로그인 사이에 시각적 간격이 있다.

#### 워크스페이스 셸

```text
최좌측: 전역 아이콘 레일
좌측: 워크스페이스 트리
중앙 상단: 원고와 위키 문서 패널
중앙 하단: 플롯 캔버스
우측: 메모 보드·위젯
```

| 영역 | UI 구성 | 시각적 특징 | UX 역할 |
| --- | --- | --- | --- |
| 전역 레일 | 주요 메뉴, 검색, 설정, 테마 아이콘 | 매우 좁고 아이콘만 사용 | 넓은 작업 공간을 확보하며 앱 영역 전환 |
| 워크트리 | 표지, 작품 정보, 에피소드와 위키 계층 | 흰 배경, 보라색 포인트, 펼침 화살표 | 한 작품의 전체 구조 탐색 |
| 문서 패널 | 패널 제목, 상태 점, 검색·닫기, 본문 | 패널마다 선명한 테두리 | 여러 문서를 독립된 창처럼 인식 |
| 속성 영역 | 태그, 등급, 장르와 속성 표 | 파랑·회색 칩과 표 형태 | 설정을 빠르게 훑고 수정 |
| 캔버스 | 점 격자, 노드, 연결선, 줌 도구 | 넓은 바탕과 플로팅 도구 | 플롯과 관계 시각화 |
| 메모 보드 | 검색, 노란 테두리의 메모 카드 | 다른 패널보다 강한 강조색 | 짧은 참고 정보를 빠르게 식별 |
| 도움말 | 우측 하단 플로팅 버튼 | 노란 원형 버튼 | 현재 위치에서 도움말 접근 |

#### 색상과 대비

- 흰색과 옅은 회색이 기본 작업 배경이다.
- 보라색은 작품 구조와 브랜드를 나타내는 주요 포인트로 사용한다.
- 파랑, 초록, 노랑은 링크, 저장·활성 상태, 메모처럼 기능 의미에 따라 사용한다.
- 패널 간 경계는 배경 명도보다 테두리와 분할선에 의존한다.
- 다양한 기능색이 동시에 보여 펜시브보다 화면이 활발하지만 정보 밀도도 높다.

참고할 점은 여러 창이 열려도 경계를 쉽게 식별할 수 있다는 것이다. 반면 모든 패널에 테두리와 상태색을 사용하면 원고보다 UI 구조가 먼저 보일 수 있다.

#### 타이포그래피

- 패널 제목과 문서 제목은 굵기와 크기로 계층을 분리한다.
- 본문은 밝은 배경에서 높은 대비를 사용한다.
- 속성과 칩은 작은 크기로 압축해 한 화면에 많은 정보를 표시한다.
- 캐릭터가 등장하는 로그인은 둥글고 친근한 인상의 UI 문구를 사용한다.
- 실제 워크스페이스는 기능 중심의 중립적인 문체와 조밀한 텍스트를 사용한다.

브랜드 화면과 작업 화면의 문체까지 다르게 느껴질 수 있다. Lorekeeper에서는 진입부터 편집기까지 같은 브랜드 어조와 타이포그래피 위계를 유지하는 것이 좋다.

#### 컴포넌트와 상태 표현

- 각 문서 패널에는 제목, 상태 점, 검색과 닫기 버튼이 반복된다.
- 속성은 칩과 표로 표현하여 읽기와 편집의 위치를 고정한다.
- 워크트리는 문서 종류별 아이콘과 색으로 구분한다.
- 플롯 캔버스는 노드, 연결선, 미니맵과 줌 도구를 사용한다.
- 메모는 별도의 카드 스타일을 사용해 긴 문서와 구분한다.
- 위젯은 드래그, 접기와 크기 조정을 지원한다.

패널이 독립적으로 조작된다는 점은 명확하지만, 모든 패널에 제어 아이콘이 반복되어 화면이 복잡해질 수 있다. Lorekeeper에서는 패널을 활성화했을 때만 제어를 노출하는 방식도 검토할 수 있다.

#### 뮤블 UI의 강점과 위험

| 강점 | 위험 |
| --- | --- |
| 여러 자료를 동시에 열어도 패널 경계가 명확함 | 테두리와 제어 아이콘이 많아 시각적 소음이 큼 |
| 밝은 원고 화면이 장시간 읽기에 익숙함 | 기능색이 늘어나면 상태 의미가 충돌할 수 있음 |
| 작품 트리의 아이콘과 들여쓰기가 직관적임 | 좁은 전역 레일의 아이콘 의미가 불명확할 수 있음 |
| 위젯과 캔버스를 자유롭게 배치할 수 있음 | 기본 화면이 사용자 설정에 따라 불안정해질 수 있음 |
| 메모·위키·원고가 시각적으로 구분됨 | 로그인과 작업 화면의 브랜드 일관성이 약함 |

### 9.3 UI 비교 요약

| 기준 | 펜시브 | 뮤블 | 참고할 판단 |
| --- | --- | --- | --- |
| 전체 인상 | 절제된 전문 생산성 도구 | 친근한 브랜드와 기능적 데스크톱 도구 | Lorekeeper는 신뢰성과 창작성을 함께 표현 |
| 기본 테마 | 어두운 무채색 | 밝은 작업 화면 중심 | 두 테마를 지원하되 기본값은 사용자 검증 |
| 화면 구분 | 명도 차이와 얇은 선 | 명확한 테두리와 분할선 | 필요한 수준의 경계만 사용 |
| 원고 강조 | 넓은 여백과 제한된 본문 폭 | 독립 문서 패널과 높은 대비 | 원고가 항상 첫 시선이 되게 함 |
| 탐색 | 메뉴와 파일 트리 통합 | 전역 레일과 워크트리 분리 | 정보 구조 규모에 따라 한 단계 줄이는 방안 검토 |
| 보조 정보 | 우측 패널 또는 다른 파일 | 위젯과 독립 패널 | 선택에 반응하는 맥락 인스펙터 우선 |
| 상태 표현 | 제한된 색상과 작은 칩 | 여러 기능색, 점, 칩과 테두리 | 색상+아이콘+텍스트를 함께 사용 |
| 숙련 기능 | 검색·명령·아이콘 중심 | 우클릭·위젯·드래그 중심 | 초보용 노출 액션과 숙련자 단축키 병행 |
| 정보 밀도 | 중간, 원고 중심 | 높음, 다중 패널 중심 | 기본은 낮게, 분석 모드에서 단계적으로 확장 |

### 9.4 참고할 UI 원리

- 원고가 열리면 제목과 본문이 가장 높은 시각적 우선순위를 갖는다.
- 파일 트리는 들여쓰기, 아이콘, 선택 상태와 펼침 상태를 함께 사용한다.
- 현재 열려 있는 문서와 현재 선택한 트리 항목을 서로 구분한다.
- 본문 폭을 제한해 넓은 모니터에서도 한 줄이 지나치게 길어지지 않게 한다.
- 패널을 열고 닫아도 원고의 커서와 스크롤 위치를 유지한다.
- 저장·동기화·분석 상태는 작업을 방해하지 않으면서 지속적으로 확인할 수 있게 한다.
- 복잡한 기능은 선택, 우클릭, 명령 검색처럼 사용 맥락 안에서 노출한다.
- 상태는 색상 하나에만 의존하지 않고 아이콘이나 텍스트를 함께 사용한다.
- 넓은 화면에서는 비교를 지원하되 원고의 최소 작업 폭을 침범하지 않는다.

### 9.5 그대로 복제하지 않을 UI 요소

- 펜시브와 동일한 검정 기반 IDE형 셸과 상단 검색 배치
- 펜시브의 좌측 트리 구성, 아이콘 조합, 탭과 댓글 패널 형태
- 펜시브 타임라인의 색상 레일과 카드 모양
- 뮤블의 최좌측 아이콘 레일과 워크트리 비율
- 뮤블의 흰색 다중 패널, 패널 헤더와 테두리 구조
- 뮤블 메모 카드의 노란 테두리와 플로팅 도움말 버튼
- 뮤블 로그인 화면의 대형 배경 문자, 캐릭터와 인증 버튼 구성
- 두 서비스의 라벨, 마이크로카피, 상태색과 아이콘 위치

UI 분석 결과는 디자인 선택지를 넓히는 참고 자료로만 사용한다. 실제 컴포넌트와 화면은 Lorekeeper의 사용자 과업, 브랜드와 접근성 기준으로 별도 설계한다.

## 11. 전면 재구축 대상

프론트엔드는 기존 화면을 수정하는 방식이 아니라 다음 페이지와 상태를 새로 정의한다.

| 페이지·영역 | 핵심 사용자 과업 | UX 설계의 중심 |
| --- | --- | --- |
| 로그인·진입 | 빠르게 서비스 시작 | 브랜드 일관성, 최소 단계, 실패 복구 |
| 작품 목록 | 작업할 작품 선택·생성 | 최근 활동, 진행 상태, 미해결 오류 |
| 새 작품 | 작품 생성 후 바로 집필 | 최소 입력, 예제 선택, 첫 회차 즉시 진입 |
| 작품 홈 | 작품 전체 상태 파악 | 집필 진척, 설정 완성도, 오류 검토 상태 |
| 원고 편집기 | 쓰기·수정·저장 | 집중, 안정적 커서, 자동 저장, 빠른 참조 |
| 설정 관리 | 인물·장소·사건 정의 | 반복 참조, 관계, 원고 연결 |
| 플롯 관리 | 회차와 사건 구조화 | 순서, 상태, 원고 연결 |
| 오류 탐지 | 오류 이해·검토·처리 | 근거, 영향 범위, 수정 후 상태 |
| 검색·명령 | 원하는 정보와 기능 실행 | 키보드 우선, 결과 맥락 유지 |
| 환경 설정 | 작업 방식 조정 | 기본값 우선, 점진적 개인화 |

각 페이지는 경쟁 서비스의 대응 화면을 복제하지 않고 Lorekeeper의 핵심 과업을 기준으로 새 와이어프레임을 만든다.

## 12. 권장 사용자 흐름

### 12.1 온보딩

펜시브의 프로젝트 중심 구조를 따르되 첫 원고까지의 단계를 줄인다.

```text
새 작품
→ 빈 작품 또는 예제 작품
→ 작품명 입력
→ 즉시 첫 회차 편집기
```

- 장르, 소개와 세부 템플릿은 선택 입력으로 둔다.
- 예제 작품은 원고, 설정, 플롯과 오류 탐지가 연결된 완성형 구조로 제공한다.
- 첫 화면에서 모든 기능을 설명하지 않고 실제 작업 중 필요한 순간에 안내한다.

### 12.2 기본 집필

```text
작품 선택
→ 최근 회차 또는 새 회차
→ 원고 작성
→ 자동 저장 상태 확인
→ 인물·설정 선택
→ 관련 설정 또는 오류 근거 확인
→ 원래 커서 위치에서 계속 집필
```

### 12.3 오류 검토

```text
오류 알림
→ 원고의 해당 문장으로 이동
→ 관련 설정과 근거 확인
→ 수락·보류·오탐 처리
→ 원고 또는 설정 수정
→ 재분석 결과 확인
```

오류 검토는 별도의 분석 대시보드에 고립시키지 않는다. 사용자가 원고 맥락을 유지한 채 근거를 보고 처리할 수 있어야 한다.

## 13. 비교 모드와 맥락 패널

초기 구현은 무제한 패널 분할보다 다음 흐름에 집중한다.

- 원고 + 인물·세계관 설정
- 원고 + 오류 근거
- 원고 + 플롯 또는 다른 회차

권장 정책:

- 최초에는 최대 두 개의 맥락만 동시에 비교한다.
- 원고의 최소 가독 폭을 항상 보장한다.
- 좁은 화면에서는 보조 맥락을 드로어나 오버레이로 전환한다.
- 각 패널에 전체 툴바를 반복하지 않는다.
- 경쟁 서비스와 다른 패널 헤더, 분할선과 전환 방식을 디자인 시스템으로 정의한다.

뮤블처럼 사용자가 보조 도구를 직접 조립하게 하기보다 현재 선택과 행동에 따라 맥락 정보를 바꾸는 방식을 우선한다.

| 사용자 행동 | 표시할 맥락 정보 |
| --- | --- |
| 인물 이름 선택 | 인물 설정, 등장 회차, 관련 관계 |
| 문장 선택 | 메모, AI 분석, 설정 오류, 코멘트 |
| 회차 선택 | 상태, 글자 수, 목표, 버전 기록 |
| 플롯 카드 선택 | 연결된 회차와 설정 |
| 오류 선택 | 근거 문장, 관련 설정, 수정 제안 |

자주 쓰는 맥락을 고정하는 기능은 사용 데이터가 쌓인 뒤 추가한다.

## 14. 고유 UI 디자인 원칙

Lorekeeper UI는 펜시브의 어두운 생산성 도구 스타일이나 뮤블의 밝은 캐릭터 중심 스타일을 그대로 따르지 않는다. 작품의 기록, 설정의 연결과 오류의 근거라는 제품 정체성을 시각 언어로 발전시킨다.

- Lorekeeper 전용 색상 토큰, 타이포그래피 위계, 아이콘 스타일, 간격과 모션 원칙을 정의한다.
- 라이트와 다크 모드를 모두 제공한다.
- 원고 본문은 한 줄이 지나치게 길어지지 않도록 최대 폭을 둔다.
- 기본 본문은 16~18px, 1.7 안팎의 줄 간격을 출발점으로 검증한다.
- 상태 색상의 의미를 고정하고 오류, 선택, 진행 상태에 중복 사용하지 않는다.
- 아이콘만 사용하는 핵심 액션에는 툴팁과 접근 가능한 이름을 제공한다.
- 저장 중, 저장 완료, 오프라인과 충돌 상태를 지속적으로 확인할 수 있게 한다.
- 집중 모드에서는 탐색과 보조 정보를 한 번에 숨길 수 있게 한다.
- 경쟁 서비스와 동일한 아이콘 조합, 탭 형태, 패널 헤더, 카드 스타일과 마이크로카피를 사용하지 않는다.
- 설정 오류는 단순한 빨간색 경고가 아니라 심각도, 검토 상태와 근거 유형을 함께 전달하는 고유 표현을 사용한다.

## 15. UI 차별화 검토 기준

새 화면은 구현 전에 다음 기준으로 검토한다.

1. 색상을 제거해도 펜시브나 뮤블과 레이아웃이 사실상 동일하지 않은가?
2. 핵심 화면의 첫 시선이 Lorekeeper의 원고와 오류 근거로 향하는가?
3. 경쟁 서비스에는 없는 Lorekeeper 고유 과업이 화면 위계에 반영됐는가?
4. 컴포넌트의 형태와 상호작용을 디자인 시스템으로 설명할 수 있는가?
5. 경쟁 서비스의 스크린샷 없이도 동일한 설계 결정을 제품 요구로 설명할 수 있는가?
6. 단순한 색상·폰트 교체가 아니라 정보 표현과 피드백 방식이 재설계됐는가?

## 16. 구현 우선순위

### P0: 제품 골격과 핵심 편집 경험

- 로그인, 작품 목록과 새 작품 화면
- 작품→회차→원고의 기본 정보 구조
- 작품 탐색과 원고 편집기의 새 와이어프레임
- 자동 저장과 저장 상태
- 설정 및 오류 근거용 맥락 인스펙터
- 라이트·다크 모드
- 검색과 기본 단축키
- Lorekeeper 디자인 토큰과 공통 컴포넌트

### P1: 작품 구조와 오류 검토

- 원고와 설정 간 연결
- 오류 근거와 영향 범위 확인
- 플롯과 회차 연결
- 작업 맥락 전환
- 두 개 맥락 비교 모드
- 회차 상태와 버전 복원
- 예제 작품 기반 온보딩

### P2: 숙련자 기능

- 명령 팔레트
- 맥락 패널 고정과 개인화
- 고급 관계 뷰
- 작업·마감 관리
- 고급 화면 배치

## 17. 피해야 할 패턴

- 첫 프로젝트 생성 전에 장르, 설정과 템플릿을 모두 선택하게 하는 긴 온보딩
- 역할이 비슷한 파일 유형을 초기부터 많이 제공하는 구조
- 모든 고급 기능을 상단 툴바에 아이콘으로 노출하는 방식
- 화면을 직접 구성하지 않으면 기본 경험이 불완전한 위젯 시스템
- 원고 폭을 침범하는 무제한 패널 분할
- 로그인이나 결제 과정에서 설명 없이 다른 브랜드로 전환되는 흐름
- 색상이나 아이콘만으로 저장·오류·동기화 상태를 전달하는 방식
- 경쟁 서비스 레이아웃을 그대로 두고 색상과 폰트만 바꾸는 방식
- 원고와 분리된 별도 화면에서만 오류를 검토하게 하는 방식

## 18. 후속 검증 항목

실제 설계 단계에서는 다음 과제를 사용자 테스트로 검증한다.

1. 신규 사용자가 도움 없이 첫 작품과 첫 회차를 만들 수 있는가?
2. 원고를 쓰다가 등장인물 설정을 몇 초 안에 찾을 수 있는가?
3. 설정을 확인한 뒤 원래 쓰던 커서 위치로 자연스럽게 돌아오는가?
4. 저장 완료와 동기화 실패를 정확하게 이해하는가?
5. 오류 탐지 결과의 근거와 수정 방법을 이해하는가?
6. 비교 모드가 실제 집필과 검토 속도를 높이는가?
7. 다크 모드와 라이트 모드에서 장시간 읽기 피로도가 어떻게 다른가?
8. 100개 이상의 회차와 설정에서도 탐색이 가능한가?
9. 펜시브나 뮤블 경험자가 Lorekeeper를 독립된 제품으로 인식하는가?

## 19. 최종 제안

Lorekeeper는 프론트엔드를 처음부터 다시 구축한다. 펜시브처럼 프로젝트 전체의 맥락을 유지하고, 뮤블처럼 작가가 즉시 이해할 수 있는 에피소드와 설정 중심 용어를 사용하되, 화면은 설정 오류 탐지와 근거 확인이라는 Lorekeeper의 고유 작업 흐름을 중심으로 새로 설계한다.

제품 방향은 다음 한 문장으로 정리할 수 있다.

> UX 원리는 검증된 사례에서 배우고, UI는 Lorekeeper의 문제와 브랜드에서 새로 만든다.

초기 경쟁력은 기능의 개수나 경쟁 서비스와의 외형적 유사성이 아니라 원고와 설정 오류 탐지가 얼마나 자연스럽게 연결되는지에서 만들어야 한다. 자유로운 커스터마이징과 무제한 작업 공간은 핵심 흐름과 고유 UI 체계가 검증된 뒤 확장한다.
