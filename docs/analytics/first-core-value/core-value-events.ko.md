# 애널리틱스 이벤트 계약: 첫 핵심 가치 도달

상태: 가입과 프로젝트 이벤트는 로컬에 구현했다. 배포와 GA 검증은 남아 있으며 이 문서는 분석 계획을 정의한다. 현재 흐름은 [프런트엔드 동작](core-value-feature.ko.md), 가입과 프로젝트 이벤트는 [유입과 온보딩](../acquisition-onboarding/acquisition-events.ko.md), 기존 refresh 이벤트의 정의는 [refresh 이벤트](../refresh/refresh-events.ko.md)를 참고한다.

## 목표

신규 사용자가 가입과 프로젝트 생성 후 설정 문서 최신화를 처음 시작하고 결과를 반영하는지, 그 과정에 얼마나 걸리는지 측정한다. 반영 성공(`refresh_applied`)은 관찰 가능한 목표 지점으로 제안하며 사용자가 모든 AI 제안을 수락했거나 가치를 얻었다는 증거로 해석하지 않는다. 실행 후 변경 없음이나 실패로 끝나면 반영에 도달하지 않으므로 `refresh_started`도 별도로 본다.

## 이벤트와 사용자 흐름

| 단계 | 이벤트 | 상태 |
| --- | --- | --- |
| 가입 | `sign_up` | 로컬 구현. 유입 문서에 정의한 대로 신규 계정의 최초 등록 커밋을 브라우저가 확인한 때, `method` 포함. 등록은 약관 동의 전이며 서비스 이용 가능을 뜻하지 않는다. |
| 프로젝트 생성 | `project_created` | 로컬 구현. 성공 시에만 전송하고 `project_type`으로 예시와 일반 프로젝트 구분. |
| 최신화 시작 | `refresh_started` | 기존 브라우저 이벤트. 실행이 포함된 시작 성공 응답을 받았을 때 전송. |
| 결과 관찰 | `refresh_result_ready` | 기존 이벤트. 브라우저가 RUNNING에서 READY로의 전환을 관찰할 때 전송하며 모든 완료 실행에서 발생하지는 않음. |
| 결과 반영 | `refresh_applied` | 기존 브라우저 이벤트. 반영 성공 응답 또는 상태 재확인으로 반영을 확인했을 때 전송. |

시작점으로 위 순서의 GA 폐쇄형 퍼널을 구성하고, 가입 코호트와 완료까지 허용할 기간을 명시적으로 정한다. 결과 준비 및 변경 없음 경로를 별도로 살핀다. `refresh_no_changes`는 실행을 시작하지 않은 경우이고 `refresh_result_no_change`는 실행 후 관찰된 변경 없음 결과다. 전체 refresh 이벤트와 실패의 의미는 기존 계약을 따른다.

GA 퍼널 탐색은 순서에 맞게 단계를 수행한 사용자를 집계하며, 실행 건수나 사용자 생애 최초 행동을 반드시 의미하지 않는다. 이 이벤트들은 프로젝트 ID를 보내지 않으므로 서로 다른 프로젝트에서 발생한 가입, 생성, 최신화가 연결될 수도 있다. 따라서 이 퍼널은 사용자 진행을 추정하며, 앞 단계에서 만든 프로젝트를 최신화했는지 또는 반영이 생애 최초인지 증명할 수 없다. 퍼널을 정밀하게 보이게 하려고 프로젝트나 실행 ID를 GA에 추가하지 않는다. 계정당 엄격한 최초 또는 동일 프로젝트 분석은 별도의 서버 데이터 설계와 식별·개인정보 검토가 필요하다.

## 측정값

- **활성화율:** 정한 가입 코호트에서 선택한 기간 내 `refresh_applied`에 도달한 사용자 수를 가입 단계 진입 사용자 수로 나눈다. 각 단계의 인원과 기간을 함께 표시한다. 전체 DB 계정의 비율이 아니라 GA에서 관찰된 비율이다.
- **시작률:** 같은 코호트에서 기간 내 `refresh_started`에 도달한 사용자 수를 가입 사용자 수로 나눈다. 반영률과 비교하고, 반영하지 않은 모든 경우를 이탈로 간주하지 않고 변경 없음과 실패를 살핀다.
- **목표 도달 시간:** 선택한 탐색에서 지원하는 경우 가입부터 반영까지를 포함해 순서가 맞는 관찰 단계 사이의 GA 퍼널 경과 시간을 표시하고 코호트와 기간을 명시한다. 이는 퍼널의 첫 적격 단계 순서에 대한 값이며 계정의 생애 최초 반영까지 걸린 정확한 시간이 아니다. 비교하기 전 보고 기간과 허용 기간을 정한다.
- **분류:** 해당 GA 탐색에서 차원을 지원하고 질문에 맞는 범위인 경우 최초 사용자 또는 세션 유입 경로와 `project_type`으로 비교한다. 예시와 일반 프로젝트의 경로는 다르며, 사용자 단위 분류만으로 어떤 프로젝트를 최신화했는지 추정하지 않는다.

프로젝트 생성과 최신화 사이에 두 이벤트를 추가했다. `workspace_entered`는 프로젝트와 작업공간 배치가 모두 성공적으로 로드된 뒤 해당 프로젝트 작업공간이 마운트된 동안 한 번 발생한다. 새로고침이나 재방문은 새로운 진입이다. `manuscript_saved`는 편집기의 원고 저장 성공 시 발생하며 자동 저장과 제목·속성 변경 저장도 포함한다. 파일을 가져와 저장하는 데 성공한 경우에도 발생한다. 실패한 저장과 원고가 아닌 문서는 제외한다. 성공한 저장 한 건이 이벤트 한 건이며 고유 원고 수나 최초 저장을 뜻하지 않는다. 여러 파일을 가져오면 여러 번 발생할 수 있다. 두 이벤트 모두 프로젝트·문서·사용자 식별자나 내용을 보내지 않고 기존 분석 활성화 조건을 따르는 최선형 수집이다.

원고 저장은 필수 퍼널 단계가 아닌 선택 분기로 본다. 예시 프로젝트에는 이미 원고가 있을 수 있기 때문이다. GA 라이브러리의 **LoreSentry Workspace Preparation Events** 보고서는 프로젝트 생성, 작업공간 진입, 원고 저장과 최신화 결과의 이벤트 수와 사용자 수를 비교하며, 순서가 있는 퍼널이나 정확한 프로젝트별 전환 보고서는 아니다. 새 이벤트 데이터는 배포와 수집 이후에만 표시된다.

## 검증과 한계

1. 제안한 가입·프로젝트 이벤트 구현 후 실제 신규 사용자 흐름을 시험한다. UTM 도착, 가입, 온보딩, 예시 또는 일반 프로젝트 생성, 최신화 시작, 결과 준비 관찰, 반영을 거치며 이벤트 순서와 성공 동작당 중복 여부, 비활성화·mock 모드의 미전송을 확인한다. DebugView와 정제된 실제 전송 내용을 확인한다.
2. 변경 없음, 실패, 재시도, 이미 완료된 실행이 있는 상태의 진입, 백그라운드 탭, 새로고침, 결과가 불확실한 반영을 시험한다. 브라우저가 결과 전환을 놓치거나 관찰 전에 닫힐 수 있고 다른 탭의 실행을 관찰할 수도 있다. `refresh_result_ready`가 없다는 사실만으로 실패라고 단정하지 않는다. 정확한 의미는 refresh 계약을 따른다.
3. 폐쇄형 퍼널을 구성하고 테스트 흐름에 비추어 집계와 경과 시간의 해석을 확인한다. GA 식별 방식이 브라우저나 기기를 가로질러 방문을 연결하지 못할 수 있고 차단과 동의에 따라서도 누락될 수 있다. 폐쇄형 퍼널에서는 중간 이벤트가 빠지면 실제 반영했더라도 이후 단계에서 제외된다. 맥락을 파악할 때 별도의 이벤트 건수와 서버 운영 집계를 사용하고, 이 퍼널에서 실행별 성공률을 추론하지 않는다.
4. 보고서를 정기 지표로 쓰기 전에 대상 속성에서 GA 퍼널과 파라미터 사용 가능 여부를 확인한다. GA 보고와 기여도 처리는 시간이 걸릴 수 있으며 DebugView 수신만으로 운영 보고서의 완전성을 증명할 수 없다.
