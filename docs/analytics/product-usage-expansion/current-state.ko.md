## 조사 자료

프런트엔드 [문서 안내](../../README.md), [API 호출 정리](../../API_CALLS.md), 기존 분석 계약과 로컬 [QA 범위](../../qa/coverage.md)를 출발점으로 삼았다. 공통 [프런트엔드 문서](../../../../docs/frontend/README.md), 특히 [AI 챗](../../../../docs/frontend/ai-chat.md), [설정 오류 점검](../../../../docs/frontend/setting-error-check.md), [화면 결정](../../../../docs/frontend/screens-and-decisions.md), [분석](../../../../docs/frontend/analytics.md)에서 기능 의도를 확인했다. 서비스 연결, API 어댑터, 뷰 등록과 사용자 동작 핸들러를 대조했다. QA 범위 문서는 Git에서 제외된 로컬 참고 자료이므로 다른 체크아웃에는 없을 수 있으며, 유일한 근거로 사용하지 않았다.

## 계획에 영향을 주는 자료 차이

1. 공통 프런트엔드 README와 API 어댑터 설명은 아직 과거 mock 전용·챗 미지원·최신화 미리보기 상태를 설명한다. 이 코드 조사에서는 현재 `api/index.ts`, 챗·최신화 어댑터와 더 최근 기능 문서를 우선한다. 과거 배포 주장을 현재 릴리스 보고에 옮기지 않는다.
2. 로컬 QA 범위는 뷰 8개로 적혀 있고 설정 오류 점검보다 오래됐다. 현재 등록은 9개다. QA 자료는 조사 출발점이며 최신 기능을 실제 실행했다는 증거가 아니다.
3. 기존 최신화 문서는 확정 결과 개수를 버린다고 적는다. 현재 `refresh.ts`는 반환된 `created`·`updated` 배열을 검증해 길이를 돌려주고, `graph-diff-modal.tsx`는 가능한 개수를 전송한다. 응답 유실 뒤 APPLIED 재조회만으로는 여전히 개수를 복원할 수 없다. 개수 노출만을 위한 어댑터 추가 변경은 필요 없다.
4. `DocumentSession.save()`는 오류·충돌·잠금·만료를 상태에 기록하면서도 정상 이행될 수 있다. 이를 기다렸다고 저장 성공이 되지 않는다. `saveOpenDocuments()`는 미저장 상태를 검사하지만, 현재 챗 코드는 반환된 불리언이 `false`인지 확인하지 않고 계속한다. 최신화·점검 시작은 명시적으로 확인한다. 저장 전 차단을 측정하려면 실제 가드와 결과 신호가 먼저 필요하다. 정적 관찰이며 재현한 운영 장애가 아니다.
5. 설정 오류 점검의 토스트 코드는 점검 탭이 보이면 알림을 생략하며, 모든 종료 상태가 아닌 DONE·FAILED를 다룬다. 완료·취소 분석을 토스트 콜백 하나에만 맡길 수 없다.

## 검증 범위

운영 로그인, 실제 원고 전송, 모델 호출, 파괴적 동작, GA 속성 변경과 배포를 수행하지 않았다. 기존 분석 문서는 로컬 구현과 미완료 운영 검증을 기록하고 있으며 이번 조사가 그 과거 상태를 해소하지 않는다. 구현 유무, 배포 유무, 이벤트 수신, 보고서 정확성은 적용 과정에서 각각 확인해야 한다.
