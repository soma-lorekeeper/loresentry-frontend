## Source conflicts that affect this plan

1. The shared frontend README and API adapter notes still describe an older mock-only/unsupported-chat/preview-refresh state. Current `api/index.ts`, chat/refresh adapters and the newer feature documents take precedence for this code assessment. Do not copy the older deployment claims into a current release report.
2. Local QA coverage says eight views and predates setting checks. Current registration has nine. QA is a discovery aid, not evidence that the latest feature set was executed.
3. Existing refresh documentation says confirmation counts are discarded. Current `refresh.ts` validates returned `created`/`updated` arrays, returns their lengths, and `graph-diff-modal.tsx` sends available counts. Rechecking APPLIED after a lost response still cannot reconstruct these counts. A new adapter change solely to expose counts is unnecessary.
4. `DocumentSession.save()` can resolve while recording an error/conflict/lock/expiry. Awaiting it is not proof of save success. `saveOpenDocuments()` checks unsaved state, but current chat code proceeds after its resolved boolean without checking `false`; refresh and setting-check start explicitly check it. Any proposed pre-save blocking measurement needs an actual guard and result signal first. This observation is static, not a reproduced production incident.
5. Setting-check toast code suppresses notifications when the check tab is visible, and handles DONE/FAILED rather than every terminal state. A toast callback cannot be the sole analytics owner for completion or cancellation.
