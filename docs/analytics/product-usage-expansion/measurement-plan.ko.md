## 첫 세 가지 여정

### 준비 뒤 핵심 기능 도달

가입 코호트와 7일의 관찰 기간을 출발점으로 제안한다. 관찰된 가입 → 프로젝트 생성 → 작업공간 진입 → 최신화 시작·챗 턴 시작·받아들여진 점검 시작 중 하나를 본다. 모든 사용자가 모든 기능을 쓰도록 요구하지 않고 세 분기를 따로 보고한다. 7일은 시작용 제안이며 확정된 제품 목표가 아니다.

기존 최신화 반영 이정표는 이후 별도 분기로 둔다. 예시 프로젝트에 이미 자료가 있으므로 가져오기·원고 저장은 선택적 준비 분기다. 가져오기를 필수 퍼널 단계로 넣지 않는다. 가입은 약관 동의보다 먼저이므로 서비스 접근을 증명하지 못한다. 동의·계정 결과와 기존 인증 실패로 그 공백을 조사한다.

GA의 사용자 기준 순서 있는 퍼널 탐색은 **관찰된 사용자 진행**에 사용한다. 서로 다른 프로젝트·방문·반복 시도를 이어 붙일 수 있다. 식별자를 보내지 않으므로 앞에서 만든 프로젝트의 답변·최신화인지, 계정 생애 최초 동작인지 증명하지 못한다. 닫힌 퍼널은 중간 브라우저 이벤트 하나를 놓쳐도 이후 성공을 빠뜨릴 수 있다. 기존 [첫 핵심 가치의 한계](../first-core-value/core-value-events.ko.md)를 유지한다.

### 챗: 시도·결과·활용

사용자 퍼널을 만들기 전에 send_mode·outcome별 턴 결과를 본다. 이어서 챗 열기 → 전송 → 완료 결과 → 복사·근거 요청의 사용자 순서를 살핀다. 근거 선택 뒤 실제 문서가 조회되는지 관찰하되, 이벤트 순서만으로 개별 근거와 개별 조회 문서를 조인하지 않는다.

일반 전송·재시도·수정 질문 전송을 분리한다. 재시도는 새 시도이고 대화 하나에 턴이 여러 개 있을 수 있다. 보고서가 지원하는 범위에서 완료·중단 턴의 브라우저 기준 첫 내용·전체 시간 분포를 본다. 종료를 관찰하지 못한 턴은 최종 지연에 들어오지 않는 완료 편향을 표시한다. 모델 추론 시간·서버 처리량이라고 부르지 않는다.

### 점검: 시작 수락·관찰 결과·검토

시작 요청 결과, 종료 관찰, 보고서 열람, 판정 변경 성공을 별도 패널로 둔다. 선택적 사용자 퍼널은 시작 수락 → done 관찰 → 보고서 열람 → 판정 저장이다. 대응된 실행 퍼널이 아닌 사용자 진행이라고 표시한다. 판정 입력은 선택 사항이다. 사용자는 별도 판정을 남기지 않아도 읽고 동의할 수 있다. 어긋남 없음은 참여 실패가 아니다.

실패·취소·차단·불확실한 시작을 분리한다. 취소 수락 응답은 완료와 경합할 수 있으므로 이후 실제 관찰 종료 상태를 별도로 보고한다. 과거 보고서 다시 열기는 기존 결과 활용이다. 페이지 진입 시 이미 끝난 실행은 새 완료 시계열에 넣지 않는다.

일반 동작 결과는 action별로 **관찰 결과 안의 구성비**를 비교한다. 시작·unknown·해결 수는 따로 보인다. 결과 발생 수 / 시작 발생 수가 정확한 시도 성공률을 증명하지는 않는다. 이벤트 차단·유실·다중 탭 중복·날짜 경계를 넘는 시도가 있기 때문이다. 해결은 추가 최초 결과를 만들지 않으며 원래 결과 분모에 더하지 않는다.

사용자·발생·파일·초안·문서·턴·실행·문제 구간을 명시적인 단위로 쓴다. 서로 다른 단위의 합을 전환처럼 비교하지 않는다. 적은 건수만으로 해당 질문에 맞는 분석 없이 신뢰도·통계적 유의성을 발표하지 않는다.

## 분해 기준과 보고서 설정

action·outcome, view_kind, document_type, entry_point, search_scope, send_mode와 기존 유입 source·medium·campaign부터 본다. ui_locale은 필요할 때 추가하며 GA의 브라우저 언어와 구분한다. 질문에 맞는 최초 사용자·세션 유입 범위를 고른다. 기존 project_type은 프로젝트 생성 이벤트만 설명하며 같은 사용자 여정의 모든 이후 동작에 붙는 분류가 아니다.

기존 정의·여유를 조사한 뒤 실제 보고서에서 쓸 파라미터만 맞춤 측정기준·측정항목으로 등록한다. [Google 파라미터 안내](https://developers.google.com/analytics/devguides/collection/ga4/event-parameters)는 파라미터 전송과 보고서용 등록이 별개임을 설명한다. 첫 목록을 다음처럼 제안한다.

- 측정기준: outcome, action, view_kind, document_type, entry_point, search_scope, send_mode, error_category. 해당 패널을 만들 때 feature·notice_kind, verdict, close_reason을 추가한다.
- 측정항목: 필요한 보고서에만 duration_seconds, first_content_seconds, processing_seconds, file_count, succeeded_count, failed_count, unknown_count, save_attempt_count, save_success_count, save_issue_count, active_edit_seconds. 기존 최신화 측정항목을 재사용한다.

같은 이름의 측정항목은 단위를 유지한다. 브라우저 시간과 서버 처리 시간을 구분한다. 여러 동작을 섞은 평균을 서비스 지연 하나로 쓰지 않는다. 선택한 GA 화면이 원하는 분포를 지원하는지 확인한다. 평균 등록만으로 백분위수가 생기지는 않는다.

login·signup·tutorial에 새 동의어를 만들지 않고 기존 이름을 유지한다. [Google은 자동·향상된·권장·맞춤 이벤트를 구분](https://developers.google.com/analytics/devguides/collection/ga4/events)하며 맞춤 제품 이벤트로 서비스별 공백을 채운다. 주요 이벤트 설정을 바꾸기 전 기존 구성을 조사한다. 기존 sign_up·refresh_applied는 사업 이정표 후보지만, 모든 새 이벤트나 실패가 섞인 일반 result 이벤트 전체를 주요 이벤트로 지정하면 성공한 제품 사용을 표현하지 못한다.

ID·임의 타임스탬프를 보고서의 맞춤 측정기준으로 쓰지 않는다. 값 종류가 늘어 보고서 행이 `(other)`로 묶일 수 있음은 [Google 카디널리티 안내](https://support.google.com/analytics/answer/12226705?hl=en)를 따른다. 보고서 여유·설정은 이번에 검증한 값이 아닌 적용 시 확인 사항이다.

## 탐색·재방문·운영 사실

첫 배포 뒤에는 주요 퍼널에 들어오지 않는 사용자까지 포함해 기능 간 이동과 의미 있는 동작을 하는 재방문을 본다. 돌아온 활성 관찰은 이후 관찰 날짜에 편집, 성공한 가져오기·수동 생성, 완료된 챗 턴, 점검·최신화 결과 활용 중 하나가 있는 것으로 제안한다. 백그라운드 페이지 조회만으로 이 활동 정의를 충족하지 않는다. 재방문을 비교하기 전 달력 시간대·코호트 기간을 명시한다. 이 정의에는 설정·검증이 필요하며 문서로 구현되지는 않는다.

GA는 가능한 범위의 행동 관찰이다. 브라우저 차단, 동의·활성 조건, 이탈, 네트워크 오류와 신원 변화가 영향을 준다. 정확한 계정별 재방문·동일 프로젝트 전환·과금 및 모델 비용·작업 신뢰성·취소 확인·내용 정확성은 적절한 서버 기록과 필요 시 별도 평가 설계를 요구한다. 수치를 맞추려고 내부 로그·원문을 GA로 전달하지 않는다.

따라서 첫 적용 후 검토는 제품 추세 해석보다 페이로드 품질·여정 일관성을 먼저 본다. 실패 시도·unknown을 보이게 유지하고 운영 총합은 이벤트별 신원 조인을 주장하지 않는 집계 맥락으로 사용한다.
