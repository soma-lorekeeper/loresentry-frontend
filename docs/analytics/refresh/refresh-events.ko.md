# 애널리틱스 이벤트 계약: 설정 문서 최신화

상태: 로컬 구현 완료. 배포와 운영 이벤트 수집 확인은 남아 있다. 대상 GA 속성에 커스텀 측정항목과 측정기준을 등록했다. 이 계약은 실제 작업공간에서 프런트엔드가 관찰한 최신화 흐름을 다룬다. 흐름은 [프런트엔드 동작](refresh-feature.ko.md)을 참고한다. 최신화 API를 변경하거나 서버 실행 건수를 정확히 집계한다는 뜻은 아니다.

## 목적과 조건

사용자의 최신화 시작, 브라우저가 관찰한 결과, 검토창 열기와 반영 확정, 결과의 규모와 소요 시간을 파악한다. 이 수치는 사용 행동과 최종 문서 변경 규모를 나타내며 AI 제안 수용률이 아니다.

기존 Google 태그와 활성화 조건을 따른다. 유효한 측정 ID, API 데이터 모드, `loresentry.com` 호스트가 필요하며 태그를 다시 초기화하지 않는다. mock 모드와 온보딩·투어 예시에서는 전송하지 않는다. GA 전송이 기능을 막아서는 안 된다.

## 이벤트

각 행은 발생 한 번을 뜻하며, 재시도는 새로운 시도다. 매개변수 이름과 의미는 아래에서 정한다.

| 이벤트 | 전송 시점 | 매개변수 |
| --- | --- | --- |
| `refresh_start_click` | 확인창에서 ‘최신화 시작’을 눌렀을 때. 문서 저장 전이다. | 없음 |
| `refresh_started` | 시작 응답이 성공하고 실행이 있을 때 | `input_document_count` |
| `refresh_no_changes` | 시작 응답이 성공했지만 실행이 없을 때 | 없음 |
| `refresh_start_failed` | 열린 문서 저장 또는 시작 요청에 실패했을 때. 네트워크 오류만으로 서버가 실행을 시작하지 않았다고 단정할 수 없다. | `failure_stage` |
| `refresh_result_ready` | 이 브라우저가 `RUNNING` → `READY` 전환을 관찰했을 때 | `draft_count`, `new_document_draft_count`, 유효한 경우 `duration_seconds` |
| `refresh_result_no_change` | 이 브라우저가 `RUNNING` → `NO_CHANGE` 전환을 관찰했을 때. 실행 후 결과이며 시작 전의 `refresh_no_changes`와 다르다. | 없음 |
| `refresh_result_failed` | 이 브라우저가 `RUNNING` → `FAILED` 전환을 관찰했을 때 | `failure_reason` |
| `refresh_review_opened` | 실제 검토창을 준비된 실행에 대해 열 때. 다시 열 때마다 기록한다. | 없음 |
| `refresh_apply_click` | 실제 검토창에서 ‘반영 확정’을 눌렀을 때. 작업본 저장 전이다. | 없음 |
| `refresh_apply_failed` | 작업본 저장 또는 확정이 명확히 거절되거나 실패했을 때. 네트워크 응답이 불확실한 것만으로 실패로 분류하지 않고 먼저 상태를 확인한다. | `failure_stage` |
| `refresh_applied` | 확정 응답이 성공했거나, 응답이 불확실한 뒤 상태 재확인으로 `APPLIED`를 확인했을 때. 이 브라우저가 관찰한 같은 확정 시도에는 최대 한 번만 보낸다. | 알고 있는 경우 `draft_count`, `new_document_draft_count`; 성공한 확정 응답을 받아 검증한 경우에만 `updated_document_count`, `created_document_count` |

창을 닫은 것은 실패가 아니다. 저장에 실패했거나 확정 여부를 확인하지 못한 상태에서는 반영 성공을 보내지 않는다. 거절된 시도 후 다시 시도하면 별도 시도로 센다.

## 매개변수 계약

개수는 모두 0 이상의 정수다. 값을 모르거나 유효하지 않으면 0을 대신 보내지 않고 생략한다. 0은 실제로 0이라고 확인한 경우에만 유효하다.

| 매개변수 | 출처와 의미 |
| --- | --- |
| `input_document_count` | 시작 성공 응답의 `lockedFileIds` 길이. 잠긴 입력 문서로 반환된 선택 문서 수다. 최종 변경 문서 수나 처리 중 읽은 전체 문맥 문서 수는 아니다. |
| `draft_count` | `READY` 실행 또는 검토 응답의 `counts.total`. 전체 열린 검토 작업본 수다. |
| `new_document_draft_count` | `draft_counts.new`에서 변환한 `counts.created`. 새 문서 제안 작업본 수이며 이미 생성된 문서 수가 아니다. |
| `duration_seconds` | READY 응답의 서버 시각으로 계산한 `(readyAt − startedAt)`의 초 단위 값. 하나라도 없거나 유효하지 않거나 차이가 음수면 생략한다. 서버 시작부터 결과 준비까지이며 시작 전 문서 저장이나 브라우저 폴링 지연은 포함하지 않는다. |
| `updated_document_count` | 성공한 확정 응답의 `updated` 목록 길이. 본문·속성 등의 내용이나 관계가 변경된 것으로 목록에 포함된 기존 문서 수다. |
| `created_document_count` | 성공한 확정 응답의 `created` 목록 길이. 새로 생성된 문서 수다. |
| `failure_stage` | 고정 분류. 시작 실패는 `save_documents` 또는 `start_request`, 반영 실패는 `save_draft` 또는 `confirm_request`다. 단계를 확실히 구분하지 못할 때만 `other`를 쓴다. 원본 오류 메시지는 보내지 않는다. |
| `failure_reason` | 실행 실패 시 오류 코드가 `TIMED_OUT`이면 `timeout`, 그 외에는 `other`. 원본 코드나 메시지는 보내지 않는다. |

`refresh_applied`에는 같은 실행의 실제 READY·검토 응답에서 얻은 작업본 수를 로컬에서 유지해 사용한다. 서버는 `APPLIED` 이후 열린 작업본 수를 0으로 반환하므로 이전 작업본 수로 착각해서는 안 된다. 이 브라우저가 해당 수를 얻지 못했다면 생략한다. 현재 프런트엔드 확정 어댑터는 응답 본문을 버리므로, 구현할 때 `created`와 `updated` 목록을 노출하고 검증한 뒤 길이를 보내도록 변경해야 한다. 목록의 ID는 보내지 않는다.

확정 응답을 잃고 나중에 상태 조회로 `APPLIED`를 확인했다면 알고 있는 작업본 수만 포함해 `refresh_applied`를 보내고, `updated_document_count`와 `created_document_count`는 생략한다. 상태만으로 두 개수를 복원할 수 없기 때문이다. 0을 만들어 보내거나 재확인할 때 같은 성공을 또 보내지 않는다. 측정값을 얻기 위해 확정 요청을 재전송하지 않는다.

작업본 수와 변경 문서 수는 서로 다른 단위이므로 나누어 AI 수용률이라고 해석하지 않는다. 변경된 문서에는 사용자 편집과 관계 변경도 포함될 수 있다. AI 제안의 실제 수용 여부는 이 계약 범위가 아니다.

## 개인정보·집계·구현

- 지정된 개수·시간·제한된 분류만 보낸다. 프로젝트·실행·문서·사용자 ID, 제목, 본문, 검색어, URL, 원본 오류는 커스텀 매개변수에 넣지 않는다. 기존 태그 설정과 페이지 URL·referrer 정제는 다른 자동 수집에도 계속 적용된다.
- 사용자 행동은 실제 핸들러에서 기록한다. 결과 이벤트는 감시자가 상태 전환을 관찰했을 때 보내고, 폴링할 때마다 또는 종료된 상태를 처음 읽을 때 보내지 않는다. 같은 감시자가 유지되는 동안 재렌더링이나 반복 관찰로 중복하지 않는다. 검토창을 다시 여는 것은 의도적으로 새 `refresh_review_opened`를 보낸다.
- 탭 종료·네트워크 장애·새로고침으로 누락될 수 있고 다른 곳에서 시작된 실행을 보거나 여러 탭에서 같은 전환을 관찰할 수 있다. 브라우저 이벤트는 최선형 관찰이며 정확한 서버 전체 건수나 실행별 퍼널이 아니다. 최초 검토 시간도 측정하지 않는다.
- 작업본 수는 활성 실행에 필요한 범위에서만 로컬에 유지하고 실행 ID는 전송하지 않는다. 소요 시간 계산에 브라우저가 임의로 만든 시작 시각을 서버 시각 대신 사용하지 않는다.

## GA 설정과 검증

1. 기존 태그를 이용해 구현하고 배포한다. 이벤트 이름을 GA에 미리 등록할 필요는 없다.
2. 보고서에서 필요한 숫자 매개변수는 이벤트 범위 커스텀 측정항목으로 등록한다. 실패 유형별 분석이 필요하면 `failure_stage`와 `failure_reason`을 이벤트 범위 커스텀 측정기준으로 등록한다. 생성 전 대상 속성의 사용 가능 여부와 한도를 확인한다.
3. 운영 호스트에서 애널리틱스가 켜진 상태로 GA 실시간 보고서 또는 설정된 DebugView에서 이름·값·시점을 확인한다. 일반 보고서에는 더 늦게 나타날 수 있다. 변경 없음 두 경로, 실패, READY, 검토창 재열기, 확정 성공, 응답 불확실 후 `APPLIED`를 각각 확인한다.
4. 알 수 없는 값은 생략하고 실제 0은 유지하는지, 서버 시각으로 시간을 계산하는지, 커스텀 ID·내용을 보내지 않는지, 같은 로컬 확정 성공이 중복되지 않는지, 비활성화·mock 모드에서는 전송하지 않는지 테스트한다. 문서만 작성한 것은 런타임 검증이 아니다.
