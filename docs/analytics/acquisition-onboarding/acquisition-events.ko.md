# 애널리틱스 이벤트 계약: 유입과 온보딩

상태: 로컬 구현 완료. 운영 배포와 이벤트 수신 검증은 남아 있다. 현재 흐름은 [프런트엔드 동작](acquisition-feature.ko.md), 이후 refresh 흐름은 [첫 핵심 가치 도달](../first-core-value/core-value-events.ko.md)을 참고한다.

## 목적과 조건

방문자가 어디에서 유입되고 가입, 온보딩 완료, 프로젝트 생성에 얼마나 도달하는지 측정한다. 현재 Google 태그는 유효한 측정 ID, API 데이터 모드, `loresentry.com` 호스트에서만 켜진다. 프런트엔드는 도착 후 추적기가 실행될 때와 라우트가 바뀔 때 사용자 클릭 없이 `page_view`를 보낸다. 정제된 `page_location`에는 `utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content`, `gclid`, `gbraid`, `wbraid`를 남기고 `page_referrer`도 정제한다. 별도의 UTM 이벤트는 없다. 조기 이탈, 리다이렉트, 스크립트 차단이나 분석 비활성화로 수집이 빠질 수 있으므로 실제 배포 흐름을 검증한다.

별도로 프런트엔드는 선택한 유입 정보를 브라우저에 보관했다가 조건을 만족하는 온보딩 진입 시 auth의 `user_acquisitions` 테이블로 보낸다. 최근 30일 내 마지막 비직접 유입을 선택하고 온보딩 완료 전에 계정당 최대 한 행을 기록한다. 이는 GA 가입 이벤트가 아니다. [현재 유입 구현](../../../src/features/analytics/acquisition.ts)과 [기존 GA 문서](../../../../docs/frontend/analytics.md)를 참고한다.

## 이벤트

기존 Google 태그와 활성화 조건을 재사용한다. 분석 전송은 사용자 동작을 막지 않는다. 의도, 화면 표시, 성공과 실패 이벤트는 각각 다른 시점에 보낸다. 재시도는 별도 시도이며 재렌더링으로 중복하지 않는다. 실제 흐름만 측정하고 mock과 온보딩 다시 보기는 제외한다.

| 이벤트 | 전송 시점 | 파라미터와 조건 |
| --- | --- | --- |
| `page_view` | 기존 추적기가 도착 또는 라우트 변경 시 실행될 때 | 정제된 주소와 referrer. 별도의 UTM 이벤트가 아니다. |
| `login_start` | Google 로그인 버튼 클릭 | `method: google`. 기존 사용자와 실패한 시도도 포함한다. |
| `login` | 로그인 흐름 후 유효한 인증 세션이 확인된 때 | `method: google`. 신규·기존 사용자 모두 포함하며 이 브라우저가 관찰한 성공 로그인 흐름당 한 번 보낸다. 세션 복원이나 일반 새로고침에서는 보내지 않는다. |
| `auth_failed` | 브라우저가 인증 또는 약관 요청의 명확한 실패를 관찰한 때 | `failure_stage: oauth \| terms \| session`. 확인할 수 있을 때만 제한된 `failure_reason: canceled \| expired \| rejected \| unavailable \| other`를 보낸다. 불확실한 응답은 서버 실패의 증거가 아니다. |
| `signup_terms_viewed` | 가입 약관이 실제 표시된 때 | 표시당 한 번 보내고 재렌더링으로 중복하지 않는다. 기존 계정에도 같은 화면이 표시될 수 있다면 가입으로 단정하지 않는다. |
| `sign_up` | auth 등록 트랜잭션에서 **신규 계정이 처음 커밋된 때**. 브라우저가 그 결과를 신뢰할 수 있게 확인하는 시점에 이벤트를 전송한다. | `method: google`. 신규 계정당 최대 한 번. 계정 등록은 약관 동의 전이며 서비스 이용 가능을 뜻하지 않는다. 일반 로그인, 기존 계정 약관 재동의, 온보딩 미완료 사용자의 재방문에는 보내지 않는다. |
| `tutorial_begin` | 사용자가 실제 온보딩 흐름에 처음 진입한 때 | 다시 보기 제외. 재렌더링으로 중복하지 않는다. 재방문은 새로 관찰된 진입일 수 있으므로 고유 계정 수로 단정하지 않는다. |
| `tutorial_complete` | 첫 온보딩 완료 요청이 성공한 때 | 다시 보기와 실패 제외. 완료와 프로젝트 생성은 별개다. |
| `onboarding_start_selected` | 사용자가 시작 방식을 선택하고 핸들러가 그 선택을 받은 때 | `start_choice: sample \| new \| later`. 선택 의도이며 온보딩 완료나 프로젝트 생성 성공의 증거가 아니다. 반복 선택은 별도 선택이다. |
| `project_create_started` | 예시 생성 요청을 시작하거나 유효한 일반 프로젝트 양식을 제출한 때 | `project_type: sample \| standard`. 재시도마다 별도 시도다. |
| `project_created` | 프로젝트 생성 요청이 성공한 때 | 동일한 `project_type`. 두 생성 경로에서 성공한 생성마다 한 번 보낸다. |
| `project_create_failed` | 프로젝트 생성 요청이 명확히 거절되거나 실패한 때 | 동일한 `project_type`. 확인할 수 있을 때만 제한된 `failure_reason: rejected \| unavailable \| other`를 보낸다. 불확실한 네트워크 응답만으로 서버에 프로젝트가 생성되지 않았다고 단정하지 않는다. |

계정 트랜잭션은 신규 신원을 만들 때만 등록 대기 표시를 기록한다. 기존 신원과 동시 가입에서 뒤늦게 합류한 요청은 새 표시를 만들지 않는다. OAuth 복귀 후 프런트엔드는 인증 세션 또는 유효한 약관 동의 대기 자격을 이용해 BFF를 통해 표시를 확인한다. auth는 표시를 원자적으로 삭제하고 존재 여부를 반환한다. 마이그레이션 이전 계정에는 표시를 만들지 않는다. 프런트엔드는 GA가 활성화된 경우에만 확인하며 식별자는 전송하지 않는다. 삭제 후 응답이 유실되거나 전송이 차단되거나 브라우저가 돌아오지 않으면 이벤트는 누락될 수 있다. 나중에 재시도하면 실제 계정 생성보다 늦게 관찰될 수 있으며 GA 시각과 기여는 그 관찰 시점을 따른다. 온보딩·프로젝트 이벤트는 진행 중인 등록 확인을 최대 3초 기다려 전송하지만 사용자 동작은 기다리지 않는다. 확인이 더 늦으면 이벤트 순서가 바뀔 수 있다.

이는 최선형 브라우저 측정이며 커밋된 정확한 계정 수가 아니다. 서버는 분석이 비활성화된 경우에도 대기 표시를 저장하며 확인 또는 계정 삭제 시 제거한다.

`sign_up`, `login`, `tutorial_begin`, `tutorial_complete`는 GA 권장 이벤트다. 실패한 동작에는 성공 이벤트를 보내지 않는다. 다만 이후 인증이나 약관 처리에 실패하더라도 그 전에 계정 등록은 성공했을 수 있다. 로그인 취소는 브라우저가 취소 결과를 실제로 받았을 때만 기록하며 창을 닫은 것만으로 실패를 보내지 않는다. 약관 표시는 별도 단계이며 모든 사용자에게 적용되는 것은 아니다.

`sign_up`에 UTM을 커스텀 파라미터로 복사하지 않는다. GA가 수집 가능한 유입 정보를 사용자, 세션, 주요 이벤트에 연결한다. `method`는 가입 제공자이며 유입 경로가 아니다. 계정 식별자, 이메일, 이름, 프로젝트 식별자, 사용자가 입력한 내용을 보내지 않는다. 기존 URL·referrer 정제 규칙을 따르고 캠페인 값과 페이지 제목에 개인정보가 없는지도 확인한다.

## 분석과 적용

1. Tag Assistant와 GA DebugView에서 도착 시 `page_view`와 UTM을 확인하고 Google OAuth 왕복도 검증한다. 원치 않는 추천 설정이 OAuth를 유입 경로로 잘못 잡지 않는지, 라우트 변경 시 페이지 조회가 중복되지 않는지 확인한다.
2. 위 이벤트를 배포한 뒤 성공·실패·재시도·새로고침, 온보딩 다시 보기, 예시와 일반 프로젝트, 비활성화·mock 모드를 검증한다. 실제 요청에 불필요한 식별자나 콘텐츠가 없는지 확인한다.
3. `sign_up`을 GA 주요 이벤트로 지정한다. 획득 보고서나 탐색에서 가입 수를 **최초 사용자 소스·매체**와 **세션 소스·매체** 기준으로 각각 비교한다. 기여도 분석은 주요 이벤트 기여 경로 보고서에서 확인하고 선택한 모델과 전환 확인 기간을 기록한다. 이들은 서로 다른 질문이며 세션과 이벤트 기여가 현재 DB의 30일 규칙과 같다고 볼 수 없다. `project_type`, `start_choice`, `failure_stage`, `failure_reason`은 보고서에 필요한 경우에만 이벤트 범위 맞춤 측정기준으로 등록한다.
4. 정한 기간 동안 GA 가입 추세를 신규 등록된 auth 계정 수 및 기존 유입 기록과 비교한다. 차단, 동의, 이동, 브라우저·기기 변경, 식별 설정에 따라 GA 사용자와 계정은 일치하지 않을 수 있다. 구현 전 과거 이벤트는 GA에 소급 생성되지 않는다.
5. 계정별 유입 정보가 여전히 필요한지는 별도로 결정한다. GA 검증과 이관·보존 결정이 끝날 때까지 기존 수집과 과거 기록을 유지한다. 이 제안 자체는 제거를 승인하지 않는다.
